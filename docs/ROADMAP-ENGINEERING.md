# Инженерный роадмап Arendora — приоритеты по фидбэку экспертизы

Дата: 11.11.2026 · Источник: фидбэк внешней экспертизы (CEO), два тезиса:

> «Приоритет инженерии: push-уведомления, публичный API, оффлайн-инспекции. Мобильный — там, где жилец»
>
> «Клиентам с 10+ объектами нужны роли: собственник / управляющий / бухгалтер / подрядчик. Сейчас это не показано даже на лендинге. Права доступа — не фича, а условие покупки для Business»

Статусы по каждому пункту — что уже есть, что сделано в этот релиз, что дальше.

---

## 1. Push-уведомления — **готово, пайплайн работает end-to-end**

Было до релиза: полный стек уже стоял — подписка клиента (`src/lib/push.js`, VAPID),
таблица `push_subscriptions`, триггер `notify_push` (любое вставшее уведомление в
`notifications` → pg_net → Edge Function `send-push` → web-push), UI
(`PushCard` в настройках, онбординг-диалог после входа), iOS-кейс только в
установленном PWA (`PushOnboarding`).

Сделано в этом релизе:
- Регистрация service worker при старте приложения (`src/main.jsx`), а не только
  при включении push — оболочка/оффлайн и подписка теперь доступны всем.

Следующие шаги (вне этого релиза):
- Связать переключатели в настройках (`overdue/maintenance/lease`,
  `arendora:prefs`) с генерацией уведомлений — сейчас они write-only.
- Тонкая настройка тихих часов для push (не будить ночью).

## 2. Роли команды: собственник / управляющий / бухгалтер / подрядчик — **сделано в этом релизе**

Было: роли только owner/tenant/contractor/admin, manager/accountant отсутствовали,
на лендинге ролей не было, в тарифе Business — расплывчатое «Команда и роли».

Сделано в этом релизе:
- Матрица доступа `ROLE_ACCESS` (`src/lib/config/statuses.js`) — единый источник
  прав: сайдбар, роут-гейт `RoleRoute` (прямой URL вне матрицы → 404), чип платежей
  и быстрое создание в шапке.
- Роли `manager` (управляющий — операционка) и `accountant` (бухгалтер — только
  финансы) в приглашениях и смене роли (`UsersPanel`, `localAuth`, облачный
  `createInvite` — заодно исправлена сигнатура, email больше не попадает в роль).
- Гейтинг по тарифу: роли команды — условие покупки Бизнес (`planAllowsTeam` в
  `misc.js`; в приглашении на free/start/pro менеджер/бухгалтер не предлагаются).
- Облачная схема: `supabase/patches/2026-11-11-team-roles-inspections.sql` —
  таблица `team_members`, RLS-политики доступа команды (manager — операционные
  таблицы, accountant — payments select/insert/update + документы/объекты на
  чтение), расширение `invites.role`, `claim_invite` вставляет участника в
  `team_members`, `set_user_role` валидирует новые роли.
- Лендинг: раздел «Роли и права доступа» (4 карточки + изоляция данных),
  Business-тариф называет роли явно, юридическая страница тарифов обновлена.

Следующие шаги:
- Экран команды для владельца (список `team_members`, отзыв доступа) — сейчас
  участники управляются через приглашения.
- Аудит-лог действий команды (кто что менял).

## 3. Оффлайн-инспекции — **сделано в этом релизе (v1)**

Было: понятия инспекций в продукте не было вообще; оффлайна данных тоже
(SW кэшировал только оболочку).

Сделано в этом релизе:
- Модуль инспекций: сущность `inspections` (объект, тип — приёмка / плановый /
  выезд, чек-лист `[{text, status, note}]`, заметки, статусы planned/done/cancelled),
  обе реализации бэкенда, страница `/app/inspections` (mobile-first, крупные
  тач-цели — осмотр идёт с телефона на объекте).
- Оффлайн-слой `src/lib/offline/inspections.js`: зеркало в localStorage + outbox;
  облачный режим онлайн — passthrough, офлайн — чтение зеркала / очередь мутаций,
  сброс по событию `online` (правки несинхронизированной строки вливаются в одну
  операцию, локальный create отменяется при офлайн-удалении); локальный режим —
  passthrough (localStorage и есть оффлайн-хранилище).
- Связка с push: осмотр завершён с проблемами → запись в `notifications` →
  облачный триггер отправляет push (пайплайн п.1).

Следующие шаги:
- Фото пунктов чек-листа (проблемы) через существующий `uploadFile`.
- Поток жильца: уведомление о планируемом осмотре, согласование времени.
- Шаблоны чек-листов, настраиваемые владельцем (сейчас — встроенные по типу).

## 4. Публичный API — **снят с приоритета решением CEO (11.11.2026)**

Не делаем в этом цикле. Факт: REST API на api.arendora.ru (PostgREST) уже доступен
внутри продукта — им пользуется iOS-виджет (`widget/ArendoraWidget.js`: парольный
вход → JWT → GET payments). Когда приоритет вернётся: документация по этому же
паттерну + API-ключи для серверных интеграций, вебхуки.

## 5. «Мобильный — там, где жилец» — **частично, направление задано**

Сделано в этом релизе:
- Инспекции спроектированы mobile-first (осмотр — мобильный сценарий).
- SW-регистрация на старте — надёжная установка PWA у жильцов на iOS
  (push для них работает только в установленном PWA).

Следующие шаги (в порядке приоритета):
- Портал жильца (`TenantPortal`) — аудит мобильных сценариев: оплата в два
  тапа, создание заявки с фото, показания счётчиков.
- Нижняя таб-навигация для tenant/contractor вместо сайдбара-гамбургера.
- owner-side UI назначения подрядчика на заявку (RPC `assign_request` есть,
  UI нет — известный пробел, заметен и на мобильном).

---

**Применение на прод:** SQL-патч `supabase/patches/2026-11-11-team-roles-inspections.sql`
применить к БД (`docker exec -i supabase-db psql -U supabase_admin -d postgres`) до
или вместе с выкладкой нового фронтенда — старый фронтенд с новым патчем
совместим (патч аддитивный), новый фронтенд без патча в облачном режиме
инспекции/команду не покажет.
