# Arendora

SaaS для управления арендной недвижимостью: объекты, жильцы, платежи, заявки на
обслуживание, документы и аналитика в одном интерфейсе. Дополнительно платформа
сама находит исполнителя бытовой услуги — публикует заказ на Профи.ру и ведёт
переписку с мастером от имени владельца.

Двуязычный интерфейс (RU/EN), светлая и тёмная темы, PWA, виджет на iPhone
через Scriptable.

> **Названия.** Репозиторий и папка проекта — `propmind`, продукт и домен —
> `Arendora`, npm-пакет — `arendora`. Это один и тот же проект.

| Авито | Не подключён (нет публичного API на создание заказов) |

Выкладка новой версии фронтенда на прод:

```bash
ANON_KEY=<anon-ключ из /opt/arendora/stack/.env на сервере> \
  ./deploy/build-frontend.sh root@SERVER_IP
```

Без `VITE_SUPABASE_URL` приложение работает в локальном режиме на
`localStorage` — это штатный режим для разработки и демо, а не заглушка.

## Роли

| Роль | Что видит |
|---|---|
| `owner` | Всё: объекты, жильцы, платежи, заявки, документы, аналитика, настройки |
| `tenant` | Свой портал: платежи по своей квартире, заявки, документы |
| `contractor` | Список назначенных заявок, взятие в работу, отчёт о выполнении |
| `admin` | Платформенная админка: метрики, пользователи, приглашения |

Жильцы и исполнители попадают в систему не регистрацией, а по приглашению
(код от владельца) — так они сразу привязаны к нужному объекту.

## Автоматизация

**Внутри приложения**

- Автосвязывание: при создании жильца объект получает его, статус меняется на
  «Сдаётся», создаётся первый платёж на сумму аренды.
- График на 12 месяцев одной кнопкой, с защитой от дублей по периоду.
- Автопросрочка при входе: `pending` с прошедшей датой → `overdue` + уведомление.
- Напоминание за 3 дня до платежа — силами базы (`pg_cron` + `pg_net`), без
  участия фронтенда; посуточные объекты исключены автоматически.
- Продление договора: новая дата окончания + новый график.

**Воркер Профи.ру** (`automation/`)

Заявка из раздела «Услуги» попадает в очередь `automation_orders`, воркер на
Playwright открывает браузер с сохранённым профилем Профи.ру, проходит мастер
«Создать заказ» и публикует его, результат пишется обратно в базу. Дальше он
следит за чатом: отвечает мастеру данными объекта (площадь, комнаты, тип
помещения) и гасит слежку, если заявку отменили или закрыли.

Режимы: `DRY_RUN=1` (заполняет, но не отправляет), `HEADLESS=0`, `PARALLEL_SLOTS`,
`AUTO_ENQUEUE_NEW_REQUESTS`. Подробности — `automation/README.md`.

> Браузерная автоматизация Профи.ру формально противоречит правилам площадки:
> аккаунт могут ограничить. Это осознанное решение владельца продукта, риск
> описан в `automation/README.md`.

## Архитектура

```
React 18 + Vite + Tailwind (PWA)
        │
        ├── src/lib/api/*        фасад сущностей: один интерфейс, два бэкенда
        │     ├── src/lib/data/*        localStorage (демо, разработка)
        │     └── src/lib/supabase/*    self-hosted Supabase
        │
        └── Supabase (Docker на своём VPS)
              Postgres + GoTrue + PostgREST + Realtime + Edge Runtime + Caddy
                    ▲
                    │  pg_cron → pg_net → edge-функции (письма, push)
                    │
              воркер Профи.ру (systemd, Playwright)
```

Фронтенд не знает, какой бэкенд активен: `src/lib/api/entities.js` выбирает
реализацию по наличию конфигурации. Локальный режим — полноценный, а не мок:
на нём работает демо и разработка без сервера.

Self-hosted, а не облако, — требование 152-ФЗ (ч. 5 ст. 18): данные россиян
хранятся в РФ. Полный стек Supabase на 2 ГБ RAM не влезает, поэтому Kong, Studio,
Storage и analytics выброшены, их роли выполняет Caddy.

## Запуск

```bash
npm install
npm run dev       # http://localhost:5173 — локальный режим на localStorage
npm test          # 32 теста
npm run build     # production-сборка в dist/
npm run preview   # локальный просмотр сборки
```

Быстрый старт в локальном режиме: регистрация (код подтверждения показывается
на экране) → на дашборде «Загрузить демо-данные» → 8 объектов, 5 жильцов,
полгода истории платежей, заявки и документы.

Сборка против живого API:

```bash
VITE_SUPABASE_URL=https://<адрес API> VITE_SUPABASE_ANON_KEY=<anon-ключ> npm run build
```

## Деплой

`deploy/README.md` — пошаговый переезд на свой VPS (reg.ru): подготовка сервера,
секреты, перенос данных из облака, статика, воркер, виджет.

Коротко:

```bash
node deploy/generate-keys.mjs        # секреты для stack/.env
./deploy/upload.sh root@SERVER_IP    # стек, функции, воркер
ssh root@SERVER_IP 'bash /opt/arendora/init-server.sh'
ssh root@SERVER_IP 'cd /opt/arendora/stack && docker compose up -d'
```

Домен встречается в трёх местах: хосты в `deploy/stack/Caddyfile`, две строки
allow-list в `docker-compose.yml` и `SITE_URL` / `API_EXTERNAL_URL` в `.env`;
найти все — `rg -n 'arendora\.ru' deploy/`. Пока `arendora.ru` не оплачен, для
проверки стека можно взять временное имя вида `arendora.<IP>.nip.io`: оно
резолвится в ваш IP и получает нормальный сертификат.

## Тесты

```bash
npm test
```

Покрыто: арифметика дат и график платежей (включая 31-е число и переход через
год, защита от дублей), CSV, тарифы и лимиты, полнота словарей RU/EN.

## Известные ограничения

- `supabase/schema.sql` применяется целиком в SQL Editor. Файл идемпотентный и
  версионированный (версия 4), но накатывается руками — миграционного
  инструмента нет.
- Соцвход (Яндекс/VK/Mail.ru) требует зарегистрированных приложений у
  провайдеров; без них кнопки не проходят.
- Файлы документов в локальном режиме — data-URL с лимитом 1,5 МБ.
- `package.json` версии 1.0.0 при живом продукте: версия не отражает состояние.
