# Двусторонняя система заявок: жилец → владелец → исполнитель (Supabase)

## Суть
Жилец со своего телефона сообщает о проблеме и видит статусы. Владелец назначает исполнителя и контролирует. Исполнитель берёт работу, отмечает этапы, прикрепляет фото и стоимость. Всё синхронно, между устройствами, с реальными аккаунтами.

**Бэкенд — Supabase (бесплатный тариф, без карты).** Данные уходят из localStorage в Postgres с RLS-политиками. Ключ Supabase (anon) коммитится в репозиторий — это безопасно по дизайну (он публичный, граница безопасности — RLS), поэтому работает на всех трёх хостингах (Vercel, GH Pages, Netlify) без переменных окружения.

## Фаза 0 — что сделаешь ты (5 минут)
1. supabase.com → **New project** (бесплатный тариф) → название `propmind`;
2. Скопируешь **Project URL** и **anon public key** из Settings → API;
3. Вставишь их мне (или в `.env` сам) — я вшью их в приложение.

## Фаза 1 — схема БД и RLS (я готовлю SQL, ты вставляешь в Supabase SQL Editor)
- **profiles** — `id` (= auth.users), `full_name`, `phone`, `role`: `owner | tenant | contractor`. Триггер: при создании пользователя автоматически создаётся профиль (роль из метаданных приглашения);
- **properties** — `owner_id`, `name`, `address`, `rent_amount`, `tenant_id` (→ профиль жильца), статусы и дleases;
- **payments** — как сейчас + `owner_id/tenant_id`;
- **maintenance_requests** — `owner_id`, `property_id`, `created_by` (жилец), `title`, `description`, `urgency`, `photo_url`, `status` + блок исполнителя: `contractor_id`, `contractor_status`, `work_cost`, `work_photo_url`, `work_notes`, `started_at`, `completed_at`;
- **notifications** — `user_id`, `type`, `title`, `message`, `link`, `is_read`.

**RLS-политики** (граница безопасности):
- владелец видит всё по своим объектам;
- жилец — только заявки, которые создал сам, и платежи своей квартиры;
- исполнитель — только заявки, назначенные на него, и может менять только поля исполнителя (статус/фото/стоимость);
- уведомления — только свои.

**Демо-аккаунт** сидируется SQL'ом: `owner@propmind.test / secret123` (role: owner) — кнопка «Заполнить демо-аккаунт» продолжает работать на любом устройстве.

## Фаза 2 — замена auth и data-слоя
- `src/lib/supabase/client.js` — createClient;
- `src/lib/supabase/auth.js` — вход/регистрация/приглашения через Supabase Auth (email+пароль, сброс через письмо Supabase);
- `src/lib/supabase/entities.js` — те же 5 сущностей, но таблицы Supabase; `useCollection` сохраняет свой API, realtime заменяет BroadcastChannel (обновления приходят между устройствами);
- localStorage-слой удаляется; роли `owner/tenant/contractor` вместо `admin/user` (admin остаётся как флаг для админ-панели).

## Фаза 3 — три портала
**Владелец** (как сейчас + новые возможности в «Заявках»):
- назначает исполнителя из списка (dropdown активных исполнителей);
- проверяет выполненное: видит фото и стоимость → «Принять работу» (статус `closed`) или «Вернуть»;
- приглашает жильцов (карточка объекта → email) и исполнителей (Заявки → Исполнители → Пригласить).

**Жилец** (`/app` под ролью tenant):
- «Сообщить о проблеме»: описание + фото, квартира подставлена автоматически;
- трекер статуса: Новая → Назначена → В работе → Выполнено → Принято;
- свои платежи и документы (только просмотр).

**Исполнитель** (`/app` под ролью contractor):
- «Мои работы»: список назначенных заявок с адресом и фото проблемы;
- кнопки: Принять → В работу → Завершить (обязательное фото результата + стоимость + комментарий);
- видит только своё.

## Фаза 4 — real-time и уведомления
- Подписки Supabase Realtime: заявка обновилась у исполнителя — владелец видит это мгновенно (и наоборот);
- Уведомления в БД: жильцу «заявка принята/выполнена», исполнителю «новая работа», владельцу «работа завершена» — доставляются на любом устройстве.

## Вне скоупа этой фазы (следующие шаги)
Stripe-оплаты работ, рейтинг исполнителей, чат внутри заявки, email-уведомления (нужны Edge Functions).

## Порядок работ и коммиты
1. Настройка Supabase (ты) + SQL-схема (я) → коммит `schema + клиент`;
2. Auth swap + демо-аккаунт в облаке → коммит;
3. Замена data-слоя → приложение работает у владельца как раньше, но из облака → коммит;
4. Порталы жильца и исполнителя + назначение → коммит;
5. Realtime + уведомления → коммит;
6. Деплой: Vercel + зеркало (обе сборки рабочие — данные в облаке).

Каждая фаза shippable отдельно: если прервёмся на середине, приложение остаётся рабочим.
